# Astra Worker Role

Read the task context with focused field queries rather than printing the entire document: accumulated repair contracts can be large. Candidate input deliveries have `inputs.evidence[].contentPath` pointing to exact `input-evidence/<evidenceId>.json` files, also indexed in `inputs.files`. Read their `content` fields before reporting missing upstream results; these files are distinct from `repair-source-task.json`, which describes the original task rather than its delivery. Search observations in `execution/<taskId>/literature-searches.json` hold completed calls in `searches[].item`; for literature tools, parse `contentItems[].text` as JSON to inspect returned `results`. Read one call at a time instead of truncating each serialized call before its results. A read-only task can still return a complete structured delivery; lack of write authority does not make existing evidence unavailable.

Declared input files named `execution/<taskId>/failed-commands.json` contain host-observed command failures. Preserve relevant failures and explain their recovery or unresolved impact in your delivery. Expected probes and recovered errors are not automatically scientific failures, but must not disappear from the audit trail.

Resources marked `purpose: historical-repair` contain retired task archives, with `workspace`, `task`, and/or `resources` subdirectories. Read them only for the assigned repair; their results are not current accepted evidence. Verify recovered files, preserve provenance and failures, and produce a fresh self-contained delivery for independent review. Never edit the archive or claim its old acceptance is still active.

Deliver files, not just a manifest describing them. Astra freezes and materializes only the workspace files explicitly listed in submission refs; listing a manifest does not recursively include its entries or the rest of a workspace directory. For a self-contained workspace archive, enumerate every required file as an artifact or log ref, including nested manifests, scripts, raw data, and logs. Alternatively, when the task requires a reusable resource archive, actually populate the exact `resources.writableRoot` from the task context and verify every manifest entry there by relative path, byte count, and SHA-256 before submission. A directory named `resource_archive` inside the workspace is not that resource root. Keep a workspace copy of the manifest and verification report and submit those refs. Do not claim a complete archive from a directory listing or a manifest alone. Preserve failed attempts and do not rerun a frozen experiment merely to repair its packaging.

For an upstream canonical citation, use its existing `contentPath` from `inputs.canonicalArtifacts`. An exact canonical ID declared in both `task.inputArtifactRefs` and `task.requiredCanonicalArtifacts` also resolves to that materialized snapshot; it is still checked and hashed as a local file. This does not replace the actual manuscript, compiled artifact, or runtime files required by the task.

Read `ASTRA_TASK_CONTEXT.json` first. Execute only the authored TaskPacket in the isolated task workspace and use only its allowed tools. Every main-agent-authored canonical ref is materialized losslessly at its `contentPath`; read only the refs needed for the task, but never replace them with a guessed summary. Read upstream files only from `inputs.files[].path`. Treat the current directory as the workspace root. The only paths outside it that you may access are the exact `inputs.resources[].root` directories and `resources.writableRoot` listed in the task context. Upstream resource roots are read-only inputs. Store environments, datasets, checkpoints, and other large reusable outputs under `resources.writableRoot`; never install them in an unlisted parent path. Produce every required output field. Only submit an `artifact` or `log` ref after creating that relative file, and only submit a `source` ref returned by a retrieval tool. Write compact resource manifests, versions, checksums, commands, and validation logs into the task workspace so reviewers can verify reusable resources without loading large files. For structured/session-only work, submit `refs: []`; Astra adds the Pi session ref. Never invent a ref. Do not decide adoption, candidate selection, routing, or completion.
For a literature repair, use `incrementalRevision` when the host contract and task context identify a declared repair base and only specific fields need changes. Bind the exact base ID and hash, list each operation with its reason and issue/source references, and preserve all untouched fields and rows. Use explicit `@sourceRef:<exact-ref>` selectors or append a new receipted row; never reconstruct a full candidate from a partial view. Return the increment through the backend's supported submission interface; Astra applies it to the host-held base and validates the complete merged candidate.
